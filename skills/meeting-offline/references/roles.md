# 说话人与角色认领

## 输入与来源

- 输入是会议录音，按 [转写流程](transcription.md) 取得带时间戳和说话人标记的转写；同一段录音已有的转写结果直接复用。
- 给每个文件/会议一个稳定来源编号；每位说话人的标识由“来源 + 原始说话人 ID”组成。不同文件的 A 或 speaker 0 默认不是同一个人，不自动合并成同一场会议。
- 未标注说话人的文本先标记为“说话人未分离”，不能仅凭语气分出身份。分离明显混乱时，保留受影响片段并请用户纠正。
- 转写结果和 `prepare_speakers.py` 输出里的 `separation` 说明分离做到了什么程度：`voice`（至少 90% 的发言分出了说话人）、`partial`（只分出一部分，`coverage` 是比例）、`none`（完全没分出）。不是 `voice` 时，出卡片前先如实告诉用户，例如“只有 62% 的发言分出了说话人，其余标为说话人未分离”，不要说“分离成功”或报“1 位发言人”。
- “说话人未分离”（`<来源>-UNASSIGNED`）不是一个人，卡片上照样列出这些原话，但不能认领成某一个人，也不能作为负责人或提议人的来源；`workspace.py` 会拒绝。只有用户明确说“这部分都是我/都是某某”（例如单人录音分离失败），映射里才加 `"confirm_single_speaker": true`（复核页面上是这张卡片的“这部分都是同一个人说的”勾选项）。否则用 `keep_unknown`，需要时请用户回听后逐段指认。
- Qwen 结果可用辅助脚本按来源和说话人准备证据与工作状态：

  ```bash
  python3 <skill-dir>/scripts/prepare_speakers.py \
    --source 4=/path/to/qwen-4.json \
    --source 5=/path/to/qwen-5.json \
    --out /path/to/work/meeting-state.json
  ```

  脚本只读本地 JSON，不做摘要、身份推断或网络请求。输出含完整发言证据、空的观点列表和待填角色。

## 第一阶段：逐人观点卡片

读完每人的发言，结合相邻对话理解回应关系，但不要把其他人的主张归给这个人。长会议覆盖前中后各阶段，不能只看开头几句或按发言次数选观点。

每位说话人一张卡片：

- 稳定编号，例如 `4-A`，并标明属于哪个文件。
- 一句话概括最有辨识度的主张/关注点。描述行为或内容，不写成推测职务。
- 通常 2–4 条核心观点；发言少的按实际信息量处理。区分主张、反对理由、约束、问题和本人承诺。
- 1–2 处有辨识度的原话和时间戳。摘要不能放进引号充当原话；有转写疑点时注明。不用“嗯、对、好的”作认领证据。
- 待填的“姓名或角色名”。业务称呼、职务或姓名都有效，不强制收集真实姓名。

- 本地库有相关记录时，按 [本地积累](memory.md) 预填候选（`candidate_role`）并标明待确认，不让用户从空白重填。

## 先生成、想改时确认

通常导入后直接生成完整纪要和 Todo。已确认姓名、声纹自动识别待确认姓名、说话人代号都可显示；声纹匹配只写工作区候选，不设置 `role_confirmed`，也不写长期库或声纹库。开启方式、可靠片段和阈值见 [声纹](voiceprint.md)。`UNASSIGNED` 永不参与声纹比对；用户明确通过 `confirm_single_speaker` 确认整段为同一人并绑定身份后，可显示姓名、计入参会人并作为负责人。

自动姓名在纪要网页带“待确认”标记，用户可点击确认或改名；代号也可修改。改名同步参会人、要点和 Todo，保存 HTML 保留修改，PNG 不带待确认标记。用户发回修改版后，用 `workspace.py import-html --workspace W --html 修改后的文件 --revision N` 只导入明确确认的说话人映射；不能从 HTML 导入正文、审核结果或其他状态。

### 在复核页面里认领（按需）

观点卡片和术语候选仍保留，想改时运行：

```bash
python3 <skill-dir>/scripts/review.py --workspace W --background --open
```

页面展示声纹待确认名字和相似度；相似度不是正确概率。用户选择姓名或明确保留未知，再勾选该卡片的确认选项并保存。只看页面、未勾选的预填名字不入库。已在对话确认的身份可以由助手按用户输入写入；不得替用户确认未提供的身份。

例外：云端沙箱，或开启声纹但没有认出任何人，仍先请用户确认身份或明确保留未知，再生成完整纪要。沙箱使用下方对话入口；本机优先页面。其他情况不因未确认身份或普通术语而阻塞完整纪要，内容核对的不一致另按 [本地复核](local-review.md) 处理。不要用前台长时间等待命令。

### 在对话里认领（只在这些情况）

- 在 ChatGPT、Claude.ai 等云端沙箱里运行（用户打不开本机页面，见 [云端沙箱](portability.md#云端沙箱chatgptclaudeai)）；
- `review.py` 启动失败，或用户说页面打不开；
- 用户明确说就在对话里确认。

这时把卡片发在对话里，用请求用户输入工具（如可用）或明确的文本问题收集映射；默认一条消息填写多人，用户要求时再一人一问。例如：

```text
4-A =
4-B =
5-A =
```

用户回复后，把映射写成 JSON 用 `workspace.py roles` 写入工作区（同时积累到本地库）：

```bash
python3 <skill-dir>/scripts/workspace.py roles --workspace W --file roles.json --revision N
```

```json
[
  {"key": "4-A", "name": "张三", "role_title": "产品经理", "entity_type": "person", "scope": "示例公司"},
  {"key": "4-B", "profile_id": "person-…"},
  {"key": "5-A", "keep_unknown": true}
]
```

`entity_type` 是 `person`（具体的人）或 `role`（只有角色称呼）；`profile_id` 用于用户确认了本地库里已有的人；`keep_unknown` 表示用户明确保留未知。

只有上述必须先确认身份的例外，在用户回复前保持“观点整理/待认领”（可走下方短会议快速通道）。一般本机流程直接生成。不要仅因文字提到某人就把他当成发言者。

## 短会议快速通道

仅对需要先确认身份的例外，同时满足以下条件时，把纪要草稿和认领放在同一轮里：

- 分离后实质发言人不超过 2 位；
- 只有一个来源文件，不涉及跨文件合并；
- 需要用户判断的术语不超过 2 个（可以没有）。

照常打开复核页面，在发链接的同一条消息里附上标明“草稿，待确认身份后定稿”的纪要正文，用 `4-A`、`4-B` 编号代替姓名，负责人同样写编号。在对话里认领的情况下，这条消息依次包含：每人一张精简卡片（编号、一句话关注点、1 处带时间戳的原话；有本地库候选时写成 `4-A = 张三（候选：依据……）`）、认领模板和术语问题（例如 `4-A = ？　4-B = ？　“普罗”指的是：示例Pro / 其他`）、草稿。

草稿只在聊天里给出，不生成 HTML/PNG、不归档交付物（录音仍按第 1 步归档）、不写入库。用户在页面确认后（或在对话里回复，包括“候选都对”“对”这类明确确认），直接替换编号、按用户的修改调整正文，生成 HTML 和 PNG 并归档、积累，不再追问。用户纠正卡片内容或指出说话人分离有误时，退回常规的两阶段流程。只有一位说话人时也要确认身份，不默认就是用户本人。

## 第二阶段：补全映射

- 用户确认后（页面或对话）先应用已给出的姓名、角色与合并关系；部分确认也继续推进，只追问仍影响归属的缺项。
- 用户可以说 `5-A 和 4-B 是同一人，叫零售负责人`：记录这一显式合并；没有确认就保持独立。同一角色名可能对应多人，不因同名自动合并。
- 用户可明确选择保留“身份未确认”或忽略无实质发言者；不要擅自视为同意。
- 需先确认的例外在角色映射确定或用户明确接受部分未知后，直接写纪要，不再问“是否开始”；一般流程不等待此阶段。

## 跨轮状态

- 需要跨轮继续时，把来源索引、每人的观点证据、角色映射、用户确认的合并/忽略项和待填项存到任务工作目录。优先沿用现有状态，不反复重建编号。
- `role_confirmed`、确认后的 `identity_group`、`ignored_by_user` 只依据用户明确输入更新。本机声纹可预填 `role_name`，但须同时标 `role_source: "voice_match"`、`voice_similarity`、`role_confirmed: false`；它不是用户确认，不得据此写库。
- 完成前检查：所有说话人都有处理状态，角色忠于用户输入，跨文件合并有用户依据。
